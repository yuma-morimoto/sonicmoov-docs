## 調査結果

### 結論

アンインストールは、Cognito の仕様上必須というより、現在のアプリが「1台のアプリに保持された匿名ユーザー」を会員登録の単位として扱っているために必要になっています。

具体的には、ログアウトしても次の値が維持されます。

- バックエンドの `userId`
- バックエンド API 用の `authToken`
- Flutter 側の `hasMembership`

そのため、ログアウト後に別メールアドレスで登録すると、同じバックエンドユーザーに別の Cognito アカウントを紐付ける可能性があります。現在の実装はそれを防ぐため、`hasMembership === true` の場合にメール登録を止め、アプリのアンインストールを案内しています。

ただし、アンインストールしないと絶対に登録できないという仕様ではありません。アプリ内で匿名ユーザーを新しく発行して切り替える仕組みを追加すれば、アンインストールは不要にできます。

## 1. なぜアンインストールが必要になるのか

### 会員登録前に `hasMembership` を確認している

メール登録開始時、Flutter 側の `hasMembership` を取得し、`true` なら Cognito の `signUp()` を実行せず終了しています。

index.vue

このフラグは、会員登録成功時に `true` へ変更されます。

- メール登録成功時：useCognitoAuth.ts
- SNS 登録成功時：index.vue
- 通常ログイン成功時：useCognitoAuth.ts

一方、通常のログアウトでは `hasMembership` を `false` に戻していません。

### ログアウトしても匿名ユーザーは切り替わらない

`userId` はログイン中の会員専用 ID ではなく、ログイン前の匿名ユーザーにも付与される値です。

useLoginStore.ts

アプリ初回起動時、`userId` または `authToken` がなければバックエンドに匿名ユーザーを作成し、その値を保存します。

01.firstLogin.global.ts

通常のログアウト処理は、以下を実行します。

1. Cognito のログアウト
2. Vue のストアをリセット
3. 現在の `userId` を再取得
4. WebView キャッシュを削除

useCognitoAuth.ts

しかし、ログアウト時に以下は行われません。

- Flutter 側の `userId` の削除
- Flutter 側の `authToken` の削除
- Flutter 側の `hasMembership` のリセット
- 新しい匿名ユーザーの作成

また、ログイン状態ストアのリセット処理でも、`userId` と `authToken` はリセット対象になっていません。

useLoginStore.ts

`authToken` はバックエンド API リクエストの `Auth-Token` ヘッダーに使用されます。

useNaviparkApiClient.ts

したがって、Cognito のログアウトだけが完了し、バックエンド上の匿名ユーザーは同じまま残る構成です。

### アンインストールが初期化手段になっている

Flutter 側の `hasMembership` は、`getValue('hasMembership')` / `setValue()` で管理されています。

useFlutterConnection.ts

Flutter 側の実装はこのリポジトリには含まれていないため、アンインストール時にどのストレージが確実に削除されるかは未確認です。

ただし、現在のコード上は、アンインストールによって以下をまとめて初期化する運用になっていると考えられます。

- 既存の匿名ユーザー ID
- 匿名ユーザー用 API トークン
- 会員登録済みフラグ
- WebView 内の認証関連状態

つまり、アンインストールは「別メールアドレスを登録するため」ではなく、「別の匿名バックエンドユーザーを作成するための、現在用意されている唯一の利用者向け操作」と考えるのが正確です。

## 2. バグの可能性

### 高：サインアップ再開時に `hasMembership` が更新されない

サインアップ完了には、主に以下の2経路があります。

- `COMPLETE_AUTO_SIGN_IN`
- `DONE`

`COMPLETE_AUTO_SIGN_IN` では、アカウント連携成功後に `setHasMembershipToApp(true)` を呼んでいます。

useCognitoAuth.ts

一方、認証途中で中断した後の `DONE` では、Cognito アカウント連携には成功しているものの、`setHasMembershipToApp(true)` がありません。

useCognitoAuth.ts

そのため、次の状態が発生する可能性があります。

1. `hasMembership = false` の状態で登録開始
2. 認証コード入力などの途中で中断
3. サインアップ再開後、`DONE` で連携成功
4. `hasMembership` は `false` のまま
5. ログアウト
6. 別メールアドレスの登録ガードを通過
7. 同じ匿名ユーザーへの再連携を試みる

これは今回の事象に直接関係する、明確な実装不整合の候補です。

また、`DONE` と `COMPLETE_AUTO_SIGN_IN` では、完了後の以下の処理も一致していません。

- `hasMembership` の更新
- ヘッダー用 Member Token の設定
- `userId` の更新
- 最終ログイン方法の保存

サインアップ完了処理を共通化すべき状態です。

### 中：middleware 側の会員フラグ保存を `await` していない

認証 middleware で連携成功後に次の処理を実行しています。

02.auth.global.ts

ここでは `setHasMembershipToApp(true)` に `await` が付いていません。Flutter Bridge の保存処理は非同期なので、画面遷移・WebView 再読み込み・アプリ終了と競合した場合、保存完了前に処理が進む可能性があります。

この箇所は `await setHasMembershipToApp(true)` にする必要性を検討すべきです。

### 中：メール登録と SNS 登録で事前ガードが異なる

メール登録には `hasMembership` のチェックがあります。

index.vue

一方、LINE・Apple・Google の登録入口には同じガードがありません。

index.vue

これは過去のコミット履歴上、SNS 登録では既存会員でも登録可能にする意図で追加された変更です。そのため、必ずしも単純なバグとは断定できません。

ただし、現在の挙動は次のように不統一です。

| 登録方法 | `hasMembership` の事前チェック |
|---|---:|
| メール | あり |
| LINE | なし |
| Apple | なし |
| Google | なし |

SNS 登録でも同じ匿名ユーザーに対する `connectAccount()` が実行されるため、バックエンドがどの重複を許可・拒否するかを確認する必要があります。

### 中：`getHasMembership()` の値解析が脆弱

取得値を次のように解析しています。

useFlutterConnection.ts

空文字、`"undefined"`、想定外の文字列、Flutter 側から boolean が直接返却された場合などに、`JSON.parse()` または `toLowerCase()` で例外になる可能性があります。

Bridge の実際の返却仕様を確認し、次のような値を安全に扱えるようにするべきです。

- `undefined`
- `null`
- 空文字
- `"true"` / `"false"`
- boolean の `true` / `false`
- 不正な値

## 3. 単純に `hasMembership = false` にするのは危険

ログアウト時に単純に `hasMembership` を `false` にすると、会員登録画面のガードは通過できます。

しかし、`userId` と `authToken` が同じままだと、同じバックエンドユーザーへ別の Cognito アカウントを紐付ける可能性があります。

想定される問題は以下です。

- 既存会員の利用履歴が新しいアカウントから見える
- カード、定期利用券、月極契約などのデータが混在する
- 2つのメールアドレスが同一会員情報に紐付く
- `providerId=1` の連携が重複する
- Cognito 側だけ登録済みで、バックエンド連携に失敗する
- アカウント削除・ログアウト後のデータ所有者が不明確になる

したがって、以下の変更だけでは不十分です。

- ログアウト時に `hasMembership = false`
- 会員登録画面のガードを削除
- クライアント側だけで既存会員判定を変更

重複連携の防止は、クライアントのフラグではなくバックエンド側でも原子的に行う必要があります。

## 4. アンインストール不要にする方法

### 推奨案：新しい匿名ユーザーへ切り替える

別メールアドレスを「別の会員アカウント」として登録したい場合は、次のフローが最も安全です。

1. ユーザーが「別アカウントで登録」を選択
2. Cognito をログアウト
3. 現在の会員用ストアをクリア
4. バックエンドで新しい匿名ユーザーを作成
5. 新しい `userId` と `authToken` を Flutter に保存
6. `hasMembership = false` を保存
7. 新しい匿名ユーザーを対象に会員登録を開始

擬似的にフラグだけを変更するのではなく、`userId` と `authToken` も同時に切り替えることが重要です。

この方法の注意点は、現在の匿名利用履歴が新しい匿名ユーザーへ引き継がれないことです。ログアウト画面にも、ログアウト中の利用履歴はアンインストールや端末交換で失われる旨が記載されています。

confirm.vue

そのため、画面上では次のように明示する必要があります。

- 新しいアカウントを作成すると、ログアウト中の利用履歴は引き継がれない
- 既存会員の履歴は新しいアカウントへ移行されない
- 既存会員を継続利用する場合は、ログイン画面を使用する

新しい匿名ユーザーの発行は、既存の `POST /users` がその用途で安全に使えるか、バックエンド仕様を確認してから実装すべきです。現在の API クライアントだけでは、新しい匿名ユーザー発行の挙動を断定できません。

### 別案：同じ会員に別メールアドレスを追加する

ユーザーの目的が「新しい会員を作りたい」ではなく、「同じ会員を別のメールアドレスでも使いたい」であれば、新規会員登録ではなく次の機能が適切です。

- メールアドレス変更
- 追加メールアドレスの認証
- ログイン手段の追加
- 既存 Cognito アカウントへの認証情報追加

この場合は同じ会員データを維持できるため、データ混在の危険がありません。

### 別案：複数アカウント切り替え機能

1台の端末で複数の会員を使う要件がある場合は、アカウントプロファイルを複数保持し、ログイン・ログアウト時に会員単位で切り替える設計が必要です。

この場合は、以下を会員ごとに分離する必要があります。

- Cognito セッション
- バックエンド `userId`
- `authToken`
- `hasMembership`
- 会員情報
- カード・定期利用券・申込情報などの画面状態

実装規模は大きくなりますが、将来的にアカウント切り替えを正式サポートするなら、この方式が適切です。

## 5. 推奨する対応順

### P0：仕様を確定する

まず、次のどちらを求めているかを明確にする必要があります。

1. 別の会員を新規作成したい
2. 同じ会員を別メールアドレスでも利用したい

推奨する対応は次のとおりです。

| ユーザーの目的 | 推奨実装 |
|---|---|
| 別会員を作りたい | 新しい匿名ユーザーへ切り替えてから登録 |
| 同じ会員を使いたい | メールアドレス変更・認証情報追加 |
| 複数会員を切り替えたい | アカウント切り替え機能 |

### P1：`DONE` の完了処理を修正する

`DONE` の連携成功時に、少なくとも以下を実行する必要があります。

- `setHasMembershipToApp(true)`
- ヘッダー用 Member Token の再設定
- `updateUserId()`
- ログイン方法の保存

`COMPLETE_AUTO_SIGN_IN` と `DONE` の共通完了処理としてまとめるのが望ましいです。

### P1：バックエンドで重複連携を保証する

`connectAccount()` 側で、少なくとも次を同一トランザクション内で検証するべきです。

- Cognito アカウントが別ユーザーに紐付いていない
- 同じバックエンドユーザーに同じ会員種別が重複していない
- `providerId=1` の連携が重複していない
- 検証と連携登録が同時実行で競合しない

userRepository.ts

### P2：メール・SNS のアカウント方針を統一する

SNS 登録を既存会員でも許可する仕様を維持する場合は、バックエンドで許可される連携範囲を明確にする必要があります。

逆に、1台のアプリにつき1会員という仕様なら、SNS 登録にもメール登録と同じ制御を追加すべきです。

### P2：Flutter Bridge の保存を検証する

Flutter 側で以下を確認する必要があります。

- `hasMembership` の保存先
- ログアウト時に保存値が変更されるか
- アプリ再起動時の復元タイミング
- アンインストール後に Keychain 等の値が残らないか
- `setValue()` 完了前に WebView が破棄される可能性
- `userId` / `authToken` / `hasMembership` の更新順序

## 最終判定

| 項目 | 判定 |
|---|---|
| アンインストールが Cognito の必須仕様か | 現行コードからは確認できない |
| アンインストールが必要と表示される直接原因 | ログアウト後も `userId`・`authToken`・`hasMembership` が維持されるため |
| 単純なバグの可能性 | あり。特に `DONE` のフラグ更新漏れ |
| 仕様上の制約か | 1台1会員という設計なら仕様。アカウント切り替えを求めるなら機能不足 |
| 最も安全なアンインストール不要化 | 新しい匿名ユーザーを発行して切り替える |
| 避けるべき対応 | `hasMembership` だけを `false` にして同じ `userId` を再利用する |

今回の調査ではコード変更は行っておらず、型チェック・lint・テストも実行していません。Flutter 側の Bridge 実装とバックエンドの `connectAccount` 実装を確認すれば、仕様上の制約か実装不具合かを確定できます。
