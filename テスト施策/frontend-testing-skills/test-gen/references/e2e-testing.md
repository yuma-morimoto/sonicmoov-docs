# E2Eテストの書き方

## 書くべきテスト

- ビジネス要件としてクリティカルな一連のユーザーフロー（決済フローなど）が最後まで到達できるか。
- 対象は「重要度・影響度が高いシナリオ」「もう大きく変わらなさそうな画面」「リグレッション防止の価値が高い箇所」に絞る。E2Eは実装・保守コストが高いため、広く浅く書かない。

## 書かないテスト

- 具体的なロジックやバリデーションに関する部分（単体テストの担当）。
- 詳細な見た目に関する部分（VRT・目視確認の担当）。

## 書くタイミング

- 仕様が固まったタイミング、または実装の終盤にまとめて書く。
- 今後仕様が変わる可能性がある場合は書かない（後回しにする判断を明示する）。

## 書き方

- Playwright を使用する。
- DOMに依存しない（`getByRole` / `getByText` などロール・テキストベースのロケーターを使う。クラスセレクタは使わない）。
- 1シナリオ1目的を意識する（BRIEFの原則も参考になる: ドメイン用語を使う／実データを使う／意図を書きメカニクスを書かない／本質的でない情報を削る／1シナリオ1ルール／簡潔にする）。

### テスト構成

- テストコードの構成にはPage Object Model（POM）を採用する。参考: [https://playwright.dev/docs/pom](https://playwright.dev/docs/pom)
- 画面（または画面内の主要な領域）ごとにPage Objectクラスを作成し、その対象に対するロケーターの取得・操作をカプセル化する。
- テストコード（`*.e2e.test.ts`）側は、生のロケーターやセレクタを直接書かず、Page Objectのメソッドを呼び出す形で記述する。テストはシナリオの意図（何をして何を確認するか）だけを表し、操作の詳細はPage Object側に隠す。
- 命名は対象画面・領域が分かる名前にする（例: `CheckoutPage`、`LoginPage`）。
- Page Object内のロケーター取得も、他レイヤーと同様にDOM非依存（ロール・テキストベース）を守る。

## AAA/Given-When-Thenとの対応

E2Eもテスト構造としてはGiven（前提）/When（操作）/Then（期待結果）で整理すると、シナリオの意図が明確になる。
