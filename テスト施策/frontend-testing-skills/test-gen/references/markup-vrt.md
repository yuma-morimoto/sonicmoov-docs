# マークアップ（Astro等）のテストの書き方

Astroコンポーネントテストは技術的な制約があり、`.astro`ファイル自体を直接テストすることは難しい。マークアップ案件では「ロジック」と「見た目」を分けて、それぞれ別の手段でテストする。

## 対象

- Astro等、静的サイトのマークアップ案件のインタラクション（アコーディオン、テーブルのソート/フィルタ、モーダル、スクロール制御など）と、UIの見た目。

## 書き方の原則

1. **ロジックはvitest（+happy-dom）で単体テストする。**
   - `.astro`からインタラクションロジックをフレームワーク非依存のTS（例: `src/scripts/use*.ts`）へ切り出す。
   - 切り出したロジックは純粋なTSとして、vitest + happy-domで単体テストする（書き方の原則は `references/unit-testing.md` に準拠）。
   - アコーディオンの開閉、テーブルのソート/フィルタ、モーダルの開閉、スクロール制御などの分岐・状態遷移は、この層でカバーする。
   - DOM描画結果や実際の見た目はこの層では検証しない（VRT側の役割）。
2. **見た目はPlaywright VRTで検証する。**
   - 対象ページのスクリーンショットを比較し、ピクセル単位で差分を検知する（許容差分は `maxDiffPixels` 等で設定する）。
   - 複数ビューポートで実行する。

## VRTで自動化する範囲 / 目視確認に残す範囲

| 自動化する（Playwright VRT）               | 目視確認に残す                                                                |
| ----------------------------------- | ---------------------------------------------------------------------- |
| 既存ページの意図しない見た目変化（共通コンポーネント修正の副作用検知） | 初回実装時のFigmaデザイン一致（VRTは自己参照diffのため、新規ページの初回実行はベースライン化するだけで正しさの判定にならない）  |
| レイアウト崩れ（要素の位置ズレ・重なり・欠落）             | 実機WebViewでのレンダリング（Playwrightの実行はChromium系のみ。本番がネイティブWebViewの場合は別途確認する） |
| リファクタ・SCSS変更によるリグレッション              | インタラクションの操作感（スクロールの滑らかさ、タップ反応など）                                       |
|                                     | VRT対象ページ・状態リストに未登録の画面（エラー表示・0件表示など）                                    |

## テストコード生成時の対応

1. インタラクションロジックが `.astro` に直接書かれている場合、`src/scripts/` 配下などフレームワーク非依存のTSへ切り出すことを提案する。
2. 切り出したロジックはvitest（+happy-dom）で単体テストする（`references/unit-testing.md` の原則に従う）。
3. リポジトリに既にVRTの仕組み（テスト対象ページのリスト等）があれば、新規ページ・状態をそのリストに追加する。追加を忘れると検知対象から漏れる。
4. 新規実装したページ・コンポーネントは、VRTのベースライン化だけではデザイン一致が保証されないため、Figmaとの目視突き合わせが別途必要であることをユーザーに伝える。
