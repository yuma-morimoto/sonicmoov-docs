# 単体テストの書き方（AI前提）

## 対象

- 観点1（計算・判定・状態管理）、観点2（外部連携・境界）に基づく箇所。
- 機能維持に不安のある箇所。

## 書かないテスト

- 明らかにテストしなくてもいい自明なロジック（すべての状態が見てわかるような小さいロジック）。
- ロジックのない静的なコンポーネント

## 書き方の原則

1. **振る舞いをテストする。実装に対してテストしない。**
   - 内部でどう計算しているか（実装詳細）ではなく、「この入力に対してこの結果を返す」という振る舞いを検証する。
   - 関数のリファクタリングでテストが壊れるなら、それは実装に対するテストになっている可能性が高い。

2. **純粋関数と副作用を区別する。**
   - 副作用（API呼び出し、ストレージ、現在時刻、乱数など）は依存関係としてモック・スタブに置き換える。
   - 副作用を持つ関数はできるだけ小さく切り出し、ロジック本体は純粋関数として単体テストする。

3. **テストダブルを適切に使い分ける。**
   - スタブ: 決まった値を返すだけの代替品（状態検証に使う）。
   - モック: 呼び出されたかどうか・どう呼ばれたかを検証する代替品（振る舞い検証に使う）。
   - モックは必要悪であり、多用しすぎない。過剰なモックはテストの意味を薄める。

4. **AAA または Given-When-Then パターンを使う。**
   - Arrange/Act/Assert、または Given/When/Then の3構造で1テストを構成する。
   - 1テストケースにつき検証したいことは1つに絞る。

5. **正常系・異常系の両方をカバーする。**
   - 特に境界値、異常値、条件分岐が多い処理を優先する。
   - 外部連携（観点2）は、成功時だけでなく通信失敗・データなし・不正なデータのケースも検討する。

## ウェブアプリとマークアップ

- ウェブアプリ: 上記の原則をそのまま適用する。
- マークアップ（Astro等）: 静的サイトではロジックが少ないことが多い。ロジックを持つ箇所（フィルタリング、フォームバリデーション等）があれば同様に単体テストを検討する。UIの見た目はVRT（`references/markup-vrt.md`）側で担保する。
