# コンポーネントテストの書き方

コンポーネントテストは**ブラックボックステスト**である。実装の詳細ではなく、ユーザーから見える結果を検証する。

## 対象

- 観点3（ユーザー操作と画面上の振る舞い）に基づく箇所。
  - 入力、クリック、選択、送信
  - バリデーションメッセージ
  - ローディング、空状態、エラー状態
  - ボタンの有効・無効
  - モーダル、アコーディオン、画面遷移
  - APIレスポンスに応じた表示

## 書かない

- 観点3の対象例に当てはまらない実装の詳細（DOM構造、CSSクラス名、内部state変数の値そのものなど）。
- 単体テストで既にロジックとして担保済みの計算・判定結果を、component層でも重複して検証すること（判定ロジック自体が単体テスト済みなら、component側ではその結果がDOMにどう反映されるかだけを見ればよい）。

## 書き方の原則

1. **DOMに依存しない。**
   - クラスセレクタや内部DOM構造を直接指定しない。
2. **クエリ優先度を守る。**
   - 優先順位: Role（`getByRole`）> Label/Placeholder/Text（`getByLabelText` / `getByPlaceholderText` / `getByText`）> Test ID（`getByTestId`、最終手段）。
   - 参考: https://testing-library.com/docs/queries/about/#priority
3. **テストダブルはスパイ・モックを活用する。**
   - APIコールなど外部依存はモックし、コンポーネント自体の振る舞いに集中する。
4. **テストを書く前に、対象がアクセシブルな実装になっているか確認する。**
   - フォーカス制御、適切なARIA属性、セマンティックなHTML要素の使用。
   - アクセシビリティが低い実装は、`getByRole` 等で要素を特定しづらく、結果としてテストが不安定（フレーキー）になりやすい。実装自体をアクセシブルにすることがテスト容易性の向上につながる。
5. **フォームは合成された状態でテストする。**
   - 入力・バリデーション・送信ボタンの有効/無効・エラー表示はセットで検証する（個々のバリデーション関数のロジックそのものは単体テスト側で担保しておく）。

## ウェブアプリとマークアップ

- ウェブアプリ: 上記の原則をそのまま適用する。
- マークアップ（Astro等）: コンポーネントテストが技術的に難しい場合がある。`references/markup-vrt.md` を参照し、VRTでの代替を検討する。
