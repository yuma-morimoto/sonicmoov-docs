## テスト実装前の準備

1. `docs/test-plan/` 配下に対象機能のテスト計画があれば読み込み、そこに書かれた観点・優先度・想定レイヤーを入力にする。
2. テスト計画が無い場合は、対象コード・要件を読み、3つのテスト観点（下記）でその場で簡易的に洗い出す。範囲が広い、または要件が固まっていない場合は `test-plan` スキルを先に使うことを提案する。
3. 対象がウェブアプリかマークアップ（Astro等）かを確認する。マークアップの場合は `references/markup-vrt.md` を参照する。
4. リポジトリに既存のテストコードがあれば、命名規則・ディレクトリ構成・使用ライブラリを確認し、それに合わせる（このスキルが提案する規約より既存の実プロジェクトの慣習を優先する）。

## テスト観点とレイヤーの対応

| #                  | 観点                                                                                 | 対応レイヤー                  |
| ------------------ | ---------------------------------------------------------------------------------- | ----------------------- |
| 1. 計算・判定・状態管理      | 金額/日付/件数計算、バリデーション、変換処理、条件分岐、状態遷移、権限・表示可否判定など                                      | 単体テスト                   |
| 2. 外部連携・境界         | API通信、Local/Session Storage、Cookie、URL・クエリ・ルーティング、その他ブラウザAPI                       | 単体テスト（境界はモック/スタブに置換）    |
| 3. ユーザー操作と画面上の振る舞い | 入力/クリック/選択/送信、バリデーションメッセージ、ローディング/空/エラー状態、ボタン有効無効、モーダル/アコーディオン/画面遷移、APIレスポンスに応じた表示 | コンポーネントテスト（ブラックボックス）    |
| クリティカルなユーザーフロー     | 決済・申込・認証など、仕様が固まった重要導線                                                             | E2Eテスト（Playwright、限定的に） |

### レイヤーごとの判断基準

**単体テスト（観点1・2）**

- 対象は純粋な計算・判定・状態管理ロジック、外部境界とのやり取り。
- 副作用（API通信、ストレージ、日時取得など）はモック・スタブに置き換え、純粋関数と副作用を区別する。
- 「実装に対して」ではなく「振る舞いに対して」テストする。内部の関数呼び出し回数など実装詳細を検証しない。
- 実装と一緒に書き、CIを常に回せる状態にする（後回しにしない）。
- 参照：`references/unit-testing.md`

**コンポーネントテスト（観点3）**

- コンポーネントテストはブラックボックステストである。DOMの内部構造やCSSクラス名には依存しない。
- クエリの優先度を守る（Testing Libraryの推奨優先度: Role → Label/Placeholder/Text → Test ID の順。詳細: [https://testing-library.com/docs/queries/about/#priority](https://testing-library.com/docs/queries/about/#priority) ）。
- テストを書く前に、対象がアクセシブルな実装になっているか（フォーカス制御、ARIA属性、セマンティックなHTML）を確認する。アクセシビリティが高いほどテスタビリティも高い。
- 参照：`references/component-testing.md`

**E2Eテスト（クリティカルフローのみ）**

- ビジネス要件としてクリティカルなユーザーフロー（決済フローなど）が最後まで到達できるかを確認する。
- 具体的なロジックやバリデーションの正確性、詳細な見た目はE2Eの対象にしない（単体・コンポーネント・VRT側で担保する）。
- 仕様が固まったタイミング、または実装の終盤にまとめて書く。
- 今後仕様が変わる可能性がある場合は書かない。
- DOMに依存しない実装にする（構造ではなくロール/テキストで要素を特定する）。
- 参照：`references/e2e-testing.md`

## 命名規則

実プロジェクトで採用されている以下の命名規則をデフォルトとする。リポジトリに別の規約が既にある場合はそちらに従う。

| レイヤー       | 実行環境                                    | 拡張子                               |
| ---------- | --------------------------------------- | --------------------------------- |
| 単体テスト      | jsdom                                   | `*.test.ts`                       |
| コンポーネントテスト | 実ブラウザ（Playwright / Vitest browser mode） | `*.browser.test.tsx`              |
| E2Eテスト     | 実ブラウザ（Playwright）                       | `*.e2e.test.ts`（既存の置き場所があればそれに従う） |

## テスト実装手順

1. テスト対象を決める（テスト計画がある場合はその項目単位、無い場合は変更・追加された実装単位）。
2. 各項目について、上記の「テスト観点とレイヤーの対応」「レイヤーごとの判断基準」に沿ってレイヤーを判定する。書くべき/書かないテストの基準は各レイヤーのreferences（`unit-testing.md`・`component-testing.md`・`e2e-testing.md`）に従う。
3. レイヤーごとの書き方ルール（`references/*.md`）に従ってテストコードを生成する。
4. テストを実行し、通ることを確認する。
5. `references/self-review-checklist.md` に沿って自己レビューを行い、指摘があれば自分で修正する。
6. 何を・どのレイヤーで・どんな観点でテストしたか（および、意図的にテストしなかったもの）を簡潔にユーザーへ報告する。
