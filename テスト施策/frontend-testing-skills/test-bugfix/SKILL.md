# 不具合修正時のテスト追加

不具合の修正時には、**不具合を再現する自動テストを書いてから修正する**。これにより、直した箇所を保証すると同時に、同じ不具合が将来再発しないようにする。

## 大原則

- 「直してからテストを書く」のではなく「テストを書いて落ちることを確認してから直す」。順序を逆にしない。
- 修正が正しいかどうかは、テストが Red → Green に変わることで確認する。修正後に手動確認だけで済ませない。
- 既存のテストを壊していないかを最後に必ず確認する。

## 手順

### 1. 手元で不具合を再現させる

- 再現手順を確認する。チケット・報告内容に手順が書かれていればそれに従う。曖昧な場合はユーザーに再現手順を確認する。
- 実際に手を動かして（または既存のテスト・ログ・スクリーンショット等から）不具合が起きることを確認する。

### 2. 不具合を発生させている最小の部分を絞り込む

- コードを注意深く調べ、原因箇所を特定する。関連するファイル・関数・コンポーネントを `Grep` / `Read` で追う。
- 原因が単一箇所とは限らない。複数の要因が絡んでいないか確認する。

### 3. 再現テストを書く

- 絞り込んだ最小の部分に対して、**現在の（バグのある）挙動では失敗し、修正後には通るような**自動テストを書く。
- テストコードの書き方・レイヤー判断は `test-gen` スキルの基準に従う（3つのテスト観点でどの層に該当するかを判断し、命名規則・書き方に沿う）。
  - 計算・判定・状態管理のバグ → 単体テスト
  - 画面上の振る舞いのバグ → コンポーネントテスト
  - 決済など重要フロー全体に関わるバグ → E2Eテスト（対象を広げすぎない。バグそのものを再現する最小限のシナリオにする）
- 再現手順をそのままテストのシナリオに落とし込む。手動確認で使った手順・入力値を具体的に使う。

### 4. テストコードを実行し、落ちる（Red）ことを確認する

- 必ず実行して失敗することを確認する。**この確認を省略しない。** 失敗しない場合、まだ不具合を正しく再現できていない。
- 想定と異なるエラーで落ちている場合は、テストの書き方自体を見直す。

### 5. 不具合を修正する

- 手順2で特定した最小の原因箇所を修正する。無関係な変更を混ぜない。

### 6. 手順3で書いたテストコードが通る（Green）ことを確認する

- 実行してパスすることを確認する。

### 7. 既存のすべてのテストを実行し、他の部分を壊していないことを確認する

- プロジェクトのテストコマンド（`npm test` / `vitest run` / `playwright test` 等、リポジトリの規約に従う）で全体を実行する。
- 失敗するテストがあれば、修正が既存の仕様を壊していないか、あるいはそのテスト自体が今回の修正で正しく更新されるべきものかを判断する。

## 完了後の報告

- 何が原因で、どの層にどんな再現テストを追加したか、修正内容と合わせて簡潔に報告する。
- 関連するテスト計画（`docs/test-plan/` 配下）がある場合、今回のバグが既存の観点で見落とされていたのか、そもそも計画に無かった観点なのかを一言添える。見落としであれば、テスト計画側の更新も検討する旨を伝える。

## やってはいけないこと

- 修正を先に行い、後から通るテストだけを書く（Red確認を飛ばす）。
- 再現に関係のない広範囲のテストを追加する（バグ修正の意図が不明瞭になる）。
- 全体テストの実行確認を省略する。
- 再現手順が曖昧なまま、推測だけでテストを書き始める。
