# テスト方針・優先度の判断材料

## 優先度の基準

- **優先度：高**
  - 手動テストを何度も繰り返すと想定される箇所
  - バグ発生時の影響度が大きい箇所（決済・申込・認証・ユーザーが必ず通る主要導線など）
- **優先度：低**
  - テスト価値が低い箇所
  - 手動テストを何度も行わない箇所
  - 仕様が決定していない、またはすぐに変更される可能性のある箇所（ただし保守性とあわせて要検討）

## リスクベーステストの考え方

- すべての機能を同じ粒度でテストしない。不具合が起きたときの影響度が高い箇所から優先的にテストする。
- 影響度だけでなく、発生しやすさ・変更頻度・事業上の重要度も合わせて見る。
- フロントエンドでは決済・申込・認証・主要導線を優先しやすい。
- E2Eテストは実装・保守コストが高いため、リスクが高いシナリオやリグレッション防止価値が高い箇所に絞る。
- エンジニアだけで判断せず、ディレクターやQA担当者と「どこが壊れると困るか」を要件定義・キックオフ時点ですり合わせるのが望ましい（可能な場合）。

## 「書く／書かない」の判断をテスト計画に明記する

判断そのものを戦略として明文化する。曖昧なまま実装フェーズに持ち越さない。

| 判断 | 意味 |
|---|---|
| 今すぐ書く | 重要度が高く、変更・不具合リスクも高い |
| 後で書く | 仕様がまだ変わりそう、または開発終盤で固まってから書く方がよい（特にE2E） |
| 書かない | 自動化コストに対して得られる価値が低い |
| 手動で確認する | 自動化より人間の確認の方が適している |

## テストを書くタイミングの目安

| テスト種別 | 書くタイミング | 主な目的 |
|---|---|---|
| 単体テスト | 実装と並行して書く。後回しにしない | ロジックや小さな単位の品質担保。CIで常に回す |
| コンポーネントテスト | 実装と並行して書く | UI・操作・状態表示の動作担保 |
| E2Eテスト | 仕様が固まったタイミング、または開発終盤にまとめて書く | 重要シナリオ・リグレッション防止 |

E2Eを早期に書きすぎると、仕様変更のたびに修正コストが発生する点に注意する。
