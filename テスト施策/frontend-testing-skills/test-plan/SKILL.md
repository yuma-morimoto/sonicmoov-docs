# テスト分析（テスト計画作成）

フロントエンドの実装に着手する**前**に、要件・仕様からテストを書くべき箇所を分析・整理し、チームに共有できる形（Markdownファイル）に文書化する。目的は「何をテストすべきか」の漏れ・冗長性を予防し、実装後に後追いでテストを書く負荷を下げること。

このスキルは分析のみを行う。実際のテストコードは書かない（コード生成は `test-gen` スキルの役割）。

## 大原則

- テストスクリプトから書き始めない。何を・なぜテストするのかを先に言語化する。
- 暗黙的な判断をやめ、チームで共通認識が持てる状態を作る。
- 網羅を目指しすぎない。工数とリスクを踏まえて優先度をつける（リスクベーステスト）。
- 「今は書かない」「手動で確認する」という判断も、明文化すれば立派な戦略である。

## 手順

### 1. テストベースを把握する

以下を確認する。無ければユーザーに確認する。

- 要件定義書・チケット・仕様書
- 画面設計書・Figma・ワイヤーフレーム
- 既存の関連実装（ある場合はコードも読み、影響範囲を把握する）
- 案件が「ウェブアプリ」か「マークアップ（Astro等の静的サイト）」かを確認する（後続の対応レイヤーが変わる）

不明点・未確定仕様がある場合は、テスト計画を作る過程で気づいたことを「不明点」として計画書に残す（仕様漏れ・認識違いの早期発見に繋がる）。

### 2. 3つのテスト観点で洗い出す

対象の機能・画面を、以下3つの観点でひとつずつ棚卸しする。各項目について**正常系**（正常な入力・操作）と**異常系**（不正な入力・操作）の両方を検討する。

| # | 観点 | 説明 | 対象例 |
|---|---|---|---|
| 1. 計算・判定・状態管理 | 入力やイベントに対して正しい計算結果・判定結果が得られるか。境界値・異常値・条件分岐が多い処理を優先する | 金額/日付/件数の計算、バリデーション、変換処理、条件分岐、複雑な状態遷移、権限や表示可否の判定 |
| 2. 外部連携・境界 | 外部とのデータの受け渡しが期待通りか。成功時だけでなく失敗・データなし・不正データも検討する | バックエンドAPI/外部API、Local/Session Storage、Cookie、URL・クエリパラメータ・ルーティング、その他ブラウザAPI |
| 3. ユーザー操作と画面上の振る舞い | ユーザー操作や状態に応じて、画面に必要な情報・結果が表れるか。内部ロジックではなく画面上で確認できる結果を見る | 入力/クリック/選択/送信、バリデーションメッセージ、ローディング/空/エラー状態、ボタンの有効・無効、モーダル/アコーディオン/画面遷移、APIレスポンスに応じた表示 |

観点ごとに書き出した項目には、後で `test-gen` が使う「想定レイヤー」を仮置きしておくとよい（詳細な判断基準は `references/layer-mapping.md` を参照）。

- 観点1・観点2 → 基本的に**単体テスト**
- 観点3 → 基本的に**コンポーネントテスト**（ブラックボックス）
- 上記に加えて、決済フローなど**ビジネス上クリティカルな一連のユーザーフロー**は個別に **E2Eテスト**候補として書き出す

### 3. テスト方針・優先度を決める

以下を明確にする（詳細な判断材料は `references/priority-and-policy.md` を参照）。

- この機能・画面でテストをどの程度書くべきか
- 自動テストでどこまで品質を担保し、どこから手動確認に残すか
- 優先度「高」（手動テストを何度も繰り返す想定の箇所／バグ発生時の影響度が大きい箇所）と「低」（テスト価値が低い、仕様未確定ですぐ変わる可能性がある）を項目ごとに付ける
- 「今すぐ書く／後で書く（仕様が固まってから）／書かない／手動で確認する」を項目ごとに判断する

### 4. マークアップ案件の場合

ウェブアプリのロジック・振る舞いのテストに加えて、UI差分検知（VRT）の対象を検討する。Astro案件のコンポーネントテストは技術的制約があるため、代替手段が必要になる場合がある。詳細・現状の検証状況は `references/markup-notes.md` を参照（この領域は社内でまだ検証中で、確定した標準ではないことに注意）。

### 5. テスト計画をMarkdownで保存する

`references/template.md` のテンプレートに沿って、以下のパスに保存する。

- 保存先: `docs/test-plan/<機能・画面のスラッグ>.md`（リポジトリに `docs/test-plan/` が無ければ作成する。既に類似の格納先の慣習がリポジトリにある場合はそちらに合わせる）
- ファイル名は機能・画面が分かる名前にする（例: `docs/test-plan/user-management-edit.md`）

保存後、どこに何を作成したかをユーザーに一言で報告する。このファイルは後続の `test-gen` スキルや、実装レビュー時に参照される想定。

### 6. チームに共有できる状態にする

- 作成したテスト計画のパスをPRの説明やチケットに書けるよう、要約（3行程度）を提示する
- テスト計画作成中に見つかった仕様漏れ・不明点があれば、実装前に確認すべき事項として明示する

## やってはいけないこと

- テスト計画を作らずにいきなりテストコードを書き始める（それは `test-gen` の仕事であり、このスキルの役割ではない）
- 観点を無視して「思いつくテスト」を並べる
- 優先度をつけずに全項目を同列に扱う
- 仕様が固まっていない箇所まで無理にテスト範囲に含める（「今は書かない」判断を許容する）
