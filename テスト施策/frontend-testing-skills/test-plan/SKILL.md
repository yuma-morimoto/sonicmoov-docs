# テスト分析

実装に着手する前に、要件・仕様からテストを書くべき箇所を分析・整理し、チームに共有できる形（Markdownファイル）に文書化する。目的は「何をテストすべきか」の漏れ・冗長性を予防し、実装後に後追いでテストを書く負荷を下げること。

このスキルは分析のみを行う。実際のテストコードは書かない（コード生成は `test-gen` スキルの役割）。

## 大原則

- テストスクリプトから書き始めない。何を・なぜテストするのかを先に言語化する。
- 暗黙的な判断をやめ、チームで共通認識が持てる状態を作る。
- 網羅を目指しすぎない。工数とリスクを踏まえて優先度をつける（リスクベーステスト）。
- 「今は書かない」「手動で確認する」という判断も、明文化すれば立派な戦略である。

## 手順

### 1. テストベースを把握する

以下を確認する。無ければユーザーに確認する。
- 要件定義・仕様・Backlogチケット
- 関連実装（ある場合はコードも読み、影響範囲を把握する）
- 案件が「ウェブアプリ」か「マークアップ（Astro等の静的サイト）」かを確認する（後続の対応レイヤーが変わる）

不明点・未確定仕様がある場合は、テスト計画を作る過程で気づいたことを「不明点」として計画書に残す（仕様漏れ・認識違いの早期発見に繋がる）。

### 2. 3つのテスト観点で洗い出す

対象の機能・画面を、以下3つの観点でひとつずつ棚卸しする。各項目について**正常系**（正常な入力・操作）と**異常系**（不正な入力・操作）の両方を検討する。

| #                  | 観点                                                      | 説明                                                                                   |
| ------------------ | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 1. 計算・判定・状態管理      | 入力やイベントに対して正しい計算結果・判定結果が得られるか。境界値・異常値・条件分岐が多い処理を優先する    | 金額/日付/件数の計算、バリデーション、変換処理、条件分岐、複雑な状態遷移、権限や表示可否の判定                                     |
| 2. 外部連携・境界         | 外部とのデータの受け渡しが期待通りか。成功時だけでなく失敗・データなし・不正データも検討する          | バックエンドAPI/外部API、Local/Session Storage、Cookie、URL・クエリパラメータ・ルーティング、その他ブラウザAPI          |
| 3. ユーザー操作と画面上の振る舞い | ユーザー操作や状態に応じて、画面に必要な情報・結果が表れるか。内部ロジックではなく画面上で確認できる結果を見る | 入力/クリック/選択/送信、バリデーションメッセージ、ローディング/空/エラー状態、ボタンの有効・無効、モーダル/アコーディオン/画面遷移、APIレスポンスに応じた表示 |

観点ごとに書き出した項目には、後で `test-gen` が使う「想定レイヤー」を仮置きしておく。テスト分析の段階では厳密な確定までは不要だが、以下の基準で仮のレイヤーを付ける。最終判断は実装時の `test-gen` スキルで行う。

- **観点1・観点2 → 基本的に単体テスト**
    - 純粋な計算・判定・状態管理ロジック、外部境界（API/Storage/Cookie/URL等）とのやり取りは、実装と切り離して単体テストで担保する。
    - 外部境界はモック・スタブに置き換えてテストする（実際のAPI通信やブラウザストレージを介さない）。
    - 通信成功時だけでなく、失敗・データなし・不正データのケースも洗い出しておく。
- **観点3 → 基本的にコンポーネントテスト（ブラックボックス）**
    - ユーザーが実際に見る・操作する結果（画面表示、状態変化）を検証する。
    - 内部の実装詳細（CSSクラス名、DOM構造、内部関数呼び出し）はテスト対象にしない。
    - 「ユーザー操作の結果、画面がどうなるか」を軸に洗い出す。
- **クリティカルなユーザーフロー → E2Eテスト**（該当するものだけを候補として書き出す）
    - ビジネス要件として絶対に壊れてはいけない一連のフロー（決済、申込、認証など）
    - 仕様が固まっている、または開発終盤で固まる見込みのフロー
    - 具体的なロジック・バリデーションの正確性や、詳細な見た目の確認はE2Eの対象にしない（それぞれ単体・コンポーネント・VRT側で担保する）

**「書かない」「手動確認に残す」候補の判断材料** — 以下に該当する項目は、この時点で明示しておく。

- 明らかにテストしなくてもいい自明なロジック（すべての状態が見てわかるような小さいロジック）
- 他のテスト（ブラックボックス側）で自然に吸収されるロジック
- 特定のコンポーネント内でしか使われない小さなプライベート関数（そのコンポーネントのブラックボックステストで吸収する）
- 仕様が決定していない、またはすぐに変更される可能性がある箇所

### 3. テスト方針・優先度を決める

以下を明確にする（詳細な判断材料は `references/priority-and-policy.md` を参照）。

- この機能・画面でテストをどの程度書くべきか
- 自動テストでどこまで品質を担保し、どこから手動確認に残すか
- 優先度「高」（手動テストを何度も繰り返す想定の箇所／バグ発生時の影響度が大きい箇所）と「低」（テスト価値が低い、仕様未確定ですぐ変わる可能性がある）を項目ごとに付ける
- 「今すぐ書く／後で書く（仕様が固まってから）／書かない／手動で確認する」を項目ごとに判断する

### 4. マークアップ案件の場合

Astro案件のコンポーネントテストは技術的制約があるため、「ロジックはVitest（+happy-dom）で単体テスト」「見た目はPlaywright VRT」の2層構成で計画する（uiMatchは不採用）。実装時の詳細な書き方は `test-gen` スキルの `references/markup-vrt.md` を参照する。

テスト計画には以下を明記する。

- 手動確認に頼っている画面・インタラクションの洗い出し
- インタラクションロジックを持つ箇所は、`.astro`からのロジック切り出し（→単体テスト対象）候補として明示する
- 新規ページ・新規コンポーネントは「実装直後にFigmaとの目視突き合わせが必要」であること（VRTのベースライン化だけでは意匠一致は保証されない）
- 既存のVRT対象ページリストがあれば、今回追加する画面・状態をそのリストに追加する必要があること
- 実機（WKWebView等ネイティブWebView）での確認が必要な場合は、その旨を手動確認範囲として残す

### 5. テスト計画をマークダウンで保存する

`references/template.md` のテンプレートに沿って、以下のパスに保存する。

- 保存先: `docs/test-plan/<機能・画面のスラッグ>.md`（リポジトリに `docs/test-plan/` が無ければ作成する。既に類似の格納先の慣習がリポジトリにある場合はそちらに合わせる）
- ファイル名は機能・画面が分かる名前にする（例: `docs/test-plan/user-management-edit.md`）

保存後、どこに何を作成したかをユーザーに一言で報告する。このファイルは後続の `test-gen` スキルや、実装レビュー時に参照される想定。

## やってはいけないこと

- テスト計画を作らずにいきなりテストコードを書き始める（それは `test-gen` の仕事であり、このスキルの役割ではない）
- 観点を無視して「思いつくテスト」を並べる
- 優先度をつけずに全項目を同列に扱う
- 仕様が固まっていない箇所まで無理にテスト範囲に含める（「今は書かない」判断を許容する）
