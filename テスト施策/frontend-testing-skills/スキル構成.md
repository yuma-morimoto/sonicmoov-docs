
## テストレイヤーの定義
- どこからどこまでのレイヤーなのか認識を標準化する
- Unit
- Component


- **test-plan**
	- テスト計画は考慮漏れをなくすために残す
		- テスト計画はチャット出力（ドキュメントはユーザーから指示があるまで作成しない）
		- 仕様が明確なところを先に計画を立てる。不確定要素は最後にまとめて質問する
		- test-genからtest-planを自動で呼び出さない（test-genだけ使いたいユーザーがいるかも）
		- test-plan実行後、test-genの実行をユーザーに促す
	1. テストベースの把握
	2. 観点別テストケースの洗い出し
		- 観点別よりレイヤー別（Unit, Component）で分けた方が良さそう
		- 観点
			- 計算・判定・状態管理
			- 外部連携・境界
			- ユーザー操作と画面上の振る舞い
	3. 書かない・手動確認に残す判断（add VRT）
	- **references/**
		- **priority-and-policy.md**
			- テスト実装の優先度
		- **template.md**
			- テスト計画テンプレート
- **test-gen**
	- **SKILL.md**
		1. 実装フロー
			- テスト着手準備
			- テスト実装後のチェック
		2. 共通ルール
		3. テスト観点と対応レイヤー
		4. ファイル命名規則
		5. テストケース命名規則
		6. モックアップ
			- むやみにモックしない、モックは外部境界のみとする、できるだけそのままの実装を使う
			- 検証対象の挙動を保有または変換する本番コードは、モックにせず「本物」のまま維持してください。分離によってテストのシグナル（信頼性）が向上する、対象の契約（コントラクト）の外部にある依存関係のみをモック化します：
				 - サービスおよびネットワークの境界
				 - テスト環境で提供されない Next.js のナビゲーションやブラウザ API
				 - 外部 SDK や処理コストの高いプロバイダー
				 - 検証対象の挙動を保有・変換しておらず、セットアップの手間がテスト本体の負担になってしまうような、独立してテスト済みの「子」の境界
		7. カバレッジ
		8. VRT
		9. Red-Green-Refactor
	- **references/**
		- **unit-test.md**
			1. 書き方ルール
			2. Astroルール（scripts）
		- **component-test.md**
			1. クエリ優先度
			2. Browser Mode 採用基準




- test-plan（テスト分析）
	- claude codeのplanみたいな役割
	- モックの範囲、利用ライブラリ、テストデータ構造、既存の共通Helperなどを分析
	- 仕様書があればそれも読む
	- このスキルの役割はJSTQBのテスト分析に基づく
- test-gen（テスト実装）
	- test-planが実行されていなければ実行する




- vrt 画面（デザイン）あるプロダクトなら全部やる
- bugfix 目的・どのように使うか？・テスト計画も変えないといけない
- 実装手法の違いを補完する（どちらかに持って行く）
	- 仕様駆動開発(SDD), 仕様を始めに書く
	- 実装前にテスト(TDD)
	- 理想：ディレクターさんと事前にすり合わせ → 考慮漏れに対処する --> test-plan必要
- 数値目標：
	- 元々人力ベースでの目標だったので、人力 vs AI+skills で計算する（この場合、ほぼ達成見込みである）
	- 数値は工数ベース算出とする（係数0.2をテストとする）
